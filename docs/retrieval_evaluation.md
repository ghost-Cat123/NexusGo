# 消息检索测评说明

## 评测对象

评测的是 Agent 的历史消息检索，不是项目代码知识问答。线上链路为：

```text
Agent 提取 target_user / target_group / 时间范围 / keywords
  -> Milvus TopK 语义召回（会话与时间标量过滤）
  -> 相似度阈值 0.67
  -> MySQL 回表原消息
  -> 候选集合覆盖全部关键词的证据校验
  -> 通过：返回语义结果；不通过：FULLTEXT 兜底或明确无结果
```

最后一层的目的不是提高“看起来相似”的候选数，而是拒绝缺少关键属性的回答。例如，聊天里提到“相机”，但没有提到“价格”，查询“相机多少钱”必须无结果，不能返回相机交接消息。

## 数据集与构建方法

| 集合 | 用途 | 语料 | 查询 | 正样本/无答案 | 标签状态 |
| --- | --- | ---: | ---: | --- | --- |
| `chat_history_retrieval_review_v1.json` | 阈值校准与回归 | 42 条、4 个会话 | 36 | 32 / 4 | `v1.0`；12 条关键查询已人工审核，其中 1 条修改 |
| `chat_history_retrieval_holdout_v0_1.json` | 固定阈值的独立复验 | 30 条、3 个会话 | 34 | 20 / 14 | 初始标注待二次人工审核，不作为简历最终口径 |

数据不是随机拼接的文本。每个会话先定义真实聊天中的事实卡片，再按以下规则构造并显式标注：

1. 每个正样本查询必须指向一个或多个确定的 `msg_id`，并记录查询类别与标注理由。
2. 无答案样本保留同一会话、同一实体或相近事件，只删除被询问的关键字段。例如语料有“猫粮在哪拿”，但没有价格，形成“猫粮多少钱”的 hard negative。
3. 查询覆盖精确词、口语改写、多约束、时间窗口和无答案五类；会话外的同类实体作为权限隔离干扰项。
4. `v1.0` 仅用于选取分数阈值 `0.67`；留出集在阈值固定后运行，不参与再次调参。
5. 测试运行时按独立 `msg_id` 写入 MySQL 和 Milvus，等待 Flush，再走真实 Embedding、检索和回表代码；结束后删除两端种子数据。

这仍是仿真自然聊天数据，不是生产用户数据。留出集完成二次人工审核前，不应将其称为“人工盲测”。

## 指标与验收

对每条正样本计算 `Recall@1/3/5`、`MRR`、`NDCG@5`、`HitRate`；对无答案样本计算误召回率（FPR）；对所有返回结果检查会话与时间越界。测试同时记录每条查询的端到端检索耗时 P50/P95（Embedding、Milvus、回表和证据校验均包含在内）。

当前自动回归门槛只针对线上 `semantic_first_fallback` 策略：

| 维度 | 验收门槛 | 含义 |
| --- | --- | --- |
| Recall@5 | `>= 0.75` | 保留足够的相关消息覆盖 |
| MRR | `>= 0.75` | 相关消息不能系统性后移 |
| 无答案 FPR | `= 0` | 当前固定 hard-negative 集不允许错误回答 |
| 会话/时间越界 | `= 0` | 权限与时间过滤是硬约束 |
| 延迟 | 记录 P50/P95 | 现阶段为观测基线，样本量不足以设为容量承诺 |

门槛是小型工程回归门槛，不是统计显著性结论。正式对外指标需要扩大样本并完成双人标注。

## 最近一次真实链路结果

环境为本机 Docker Linux 容器，连接 MySQL、Milvus 与配置的 Embedding 服务；不是阿里云服务器压测，也不代表生产容量。`semantic_first_fallback` 与当前线上逻辑一致。

| 集合 | 策略 | R@1 | R@3 | R@5 | MRR | NDCG@5 | HitRate | 无答案 FPR | 越界 | P50/P95 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- | --- |
| 校准集 v1.0 | FULLTEXT | 0.500 | 0.500 | 0.500 | 0.500 | 0.500 | 0.500 | 0.000 | 0 | 2.4/4.8ms |
| 校准集 v1.0 | 线上策略 | 0.703 | 0.766 | 0.766 | 0.781 | 0.781 | 0.781 | 0.000 | 0 | 177.8/277.5ms |
| 留出集 v0.1 | FULLTEXT | 0.750 | 0.750 | 0.750 | 0.750 | 0.750 | 0.750 | 0.000 | 0 | 2.1/3.8ms |
| 留出集 v0.1 | 线上策略 | 0.900 | 0.900 | 0.900 | 0.900 | 0.900 | 0.900 | 0.000 | 0 | 197.8/249.8ms |

与 FULLTEXT 基线相比，线上策略在校准集 `R@5` 绝对提升 `26.6` 个百分点，在留出集提升 `15.0` 个百分点；两集均未发生无答案误召回或范围越界。这里的延迟是单条聊天检索（含 Embedding）的 P50/P95，不是 WebSocket 消息端到端 P95。留出集标签尚待审核，因此这组提升用于工程验证和面试展开，不作为已人工盲审的最终宣传指标。

## 运行方式

默认运行校准集：

```bash
NEXUSGO_RUN_CHAT_HISTORY_EVAL=1 go test ./apps/agent/eval -run '^TestChatHistoryRetrievalEvaluation$' -count=1 -v
```

运行留出集：

```bash
NEXUSGO_RUN_CHAT_HISTORY_EVAL=1 \
NEXUSGO_CHAT_HISTORY_EVAL_DATASET=apps/agent/eval/testdata/chat_history_retrieval_holdout_v0_1.json \
go test ./apps/agent/eval -run '^TestChatHistoryRetrievalEvaluation$' -count=1 -v
```

离线阈值扫描仅用于开发验证，使用 `NEXUSGO_CHAT_HISTORY_EVAL_MIN_SCORE` 覆盖测试阈值；生产代码不读取该变量。固定阈值或 Embedding 模型变更后，必须先重新运行校准集，再使用未改写标签的留出集复验。

## 面试表述

“我没有把聊天检索当成泛化知识库 RAG。Agent 先把自然语言问题解析成会话、时间和关键词约束，在会话隔离的 Milvus 中做语义候选召回；候选回表后必须覆盖问题中的所有关键字段，否则走 FULLTEXT 兜底或拒答。这样避免了‘相关实体存在，但用户询问的属性并不存在’的误回答。我用一套阈值校准集和一套不参与调参的留出集跑真实 MySQL、Milvus 和 Embedding 链路，验收 Recall@5、MRR、无答案 FPR 以及会话/时间越界。当前项目使用仿真自然聊天数据，留出集标签仍需人工复核，所以我会明确说明它不是生产数据。”
